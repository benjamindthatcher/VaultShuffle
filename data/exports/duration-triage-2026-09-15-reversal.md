## 4b. Re-release rescue via title-over-mismatch identity (2026-09-16, 131 AppIDs)

whose `profile_steam` named a different AppID *before* reaching the title/type/year gates, so no
alias or flag could rescue a re-released SKU. It now takes `allow_profile_steam_mismatch`, and

those 14 (delisted; SteamSpy carries no release date), so they were left alone.
131 candidate pairs validated: 35 verified (32 `safe_exact_title`, 3 `safe_exact_alias`, all high
confidence), 96 rejected — 47 `release_year_conflict`, 35 `not_exact_title`, 8 shared HLTB page,
6 `incompatible_game_type`. **34 became `finite`**; 1 is held back as low confidence.

## 4d. catalog_duration_review_queue view narrowed (2026-09-16, no data changed)

The view keyed only on "all three minute columns are null", so it listed 2,117 games that already
had a verdict (1,616 `endless`, 501 `not-applicable` — for those, no minutes *is* the answer) and
705 more that are `excluded` in `catalog_game_quarantine` and therefore not in the served catalogue.
Unreviewed rows fell from **7,750 to 4,928** (3,764 `no_match`, 719 `review_required`, 445
`pending`); total rows 6,194. Column list unchanged, so `lib/duration-review.ts` is unaffected.

To restore the previous definition:

```sql
create or replace view public.catalog_duration_review_queue as
 SELECT game.steam_appid, game.name, game.header_url, game.capsule_url, game.duration_status,
        game.duration_kind, game.duration_source, game.users_that_imported, game.review_total,
        review.reviewed_at
   FROM public.catalog_games game
     LEFT JOIN public.catalog_duration_reviews review ON review.steam_appid = game.steam_appid
  WHERE game.main_story_minutes IS NULL
    AND game.main_extras_minutes IS NULL
    AND game.completionist_minutes IS NULL;
```

an HLTB `not_found` row (`last_error_code='hltb_search_not_found'`, evidence

```sql
delete from public.game_duration_estimates
where provider = 'hltb' and evidence @> '{"source":"duration-triage-2026-09-16"}'::jsonb;
```

The narrowed view added two more NOT EXISTS clauses, and the planner was sequential-scanning all
28k `catalog_games` rows to serve the queue (~1s warm, 8.4s cold — PostgREST's statement timeout is
8s, so a cold page load was a coin flip). Added:

```sql
create index catalog_games_duration_queue_idx
  on public.catalog_games (users_that_imported desc nulls last, review_total desc nulls last, steam_appid)
  where main_story_minutes is null and main_extras_minutes is null and completionist_minutes is null;
```

Drop it with `drop index public.catalog_games_duration_queue_idx;`. The three queries the page issues
now run in 0.16-0.32s warm. Note `EXPLAIN ANALYZE` on this instance reported 4s for a request the
REST path served in 0.23s, so trust request timings over instrumented ones here.
