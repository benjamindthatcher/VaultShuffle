# VaultShuffle 1.1 → 1.2 regression review

Reviewed 1 October 2026. Five issues were reproduced with synthetic fixtures: incomplete Wishlist ownership/taste data, missing Dashboard completion prompts, missing return-visit activity, incorrect Progress sorting, and an Added-sort edge case. These are code/fixture findings; production incidence was not measured. All five findings were fixed in the subsequent implementation pass described below, along with restoring the loading animation.

## Comparison scope

There are no version tags in this checkout. The release page identifies 1.1 as 4 September and 1.2 as 1 October. For the implementation comparison, the last main-branch commit before the coordinated 1.2 release is `bbd836e`; the release commit is `b2df227`. I also checked the later committed state at `d97b9a3` and the existing working-tree changes. The five findings below remain in both the committed release code and the reviewed working tree.

The checkout already contained extensive uncommitted work and changed during the review. Validation therefore describes the current checkout, including those pre-existing changes, rather than an isolated build of the original release commit. This review did not change application code, deploy anything, or query/write production data.

| Area | 1.1 behavior | 1.2 behavior |
| --- | --- | --- |
| Data loading | Entire connected library and activity/learning summaries in shared client state | V2 private PostgreSQL repositories, bounded bootstrap, paginated Library and on-demand details |
| Dashboard | Client-derived library statistics and notices | Whole-library SQL statistics, redesigned overview and paginated completion history |

## Findings

### 1. P1 — Wishlist treats an incomplete cache as the complete library

**Sources:** `components/wishlist/WishlistPage.tsx:94`, `components/app-shell/AppDataProvider.tsx:335`, `app/api/app-data/route.ts:35`, `lib/wishlist.ts:132`.

The V2 bootstrap hydrates only pins and the current pick. Other pages add a limited set of viewed games to an entity cache; `rememberLibraryGames` caps non-pinned entries at 200. Wishlist still passes `allGames` to its recommendation engine as the account's entire library. Its ownership checks, edition exclusions and played/completed taste seeds all depend on that array. The discovery catalogue is public and does not independently exclude an account's owned games.

On a direct visit with no pins/current pick, the cache is empty even when the account owns many games. Owned or family-accessible games can be recommended for purchase, search cards can miss their owned indication, and “For you” lacks the account's played/completed seeds. Results depend on which pages were visited beforehand; a bootstrap refresh clears that accumulated cache again.

**Reproduction:** a V2 browser fixture with an owned library, no pins/current pick, and AppID 1001 in the discovery catalogue displayed 1001 among the nine recommendations at both 1280px and 390px. Wishlist made no request for complete ownership or taste inputs. The existing connected-Wishlist test uses the legacy full-library bootstrap, so it does not cover this V2 condition.

**Recommended correction:** provide a tenant-scoped V2 recommendation input containing complete owned/family AppIDs and a bounded, representative set of played/completed seeds, or perform exclusion and scoring server-side. Do not expand the shared cache into an unbounded bootstrap.

### 2. P2 — Dashboard completion prompts disappear or undercount

**Sources:** `components/shared/CompletionClaimBanner.tsx:19`, `app/(product)/dashboard/page.tsx:78`, `lib/v2/repositories/dashboard-core.ts:41`.

The Dashboard repository computes `completionSuggestions`, but the notice still runs `findCompletionCandidates(games)` against the shared entity cache. Dashboard hydrates most-played, recent-completion and value highlights; it does not hydrate every completion candidate. A qualifying game outside those highlights is therefore omitted. With no relevant cached games the notice disappears entirely, even though `/finished` has work to review.

**Reproduction:** the Dashboard response contained one eligible completion suggestion and a separate non-qualifying highlight. The completion prompt count was zero at both desktop and mobile widths.

**Recommended correction:** make the V2 notice consume an authoritative candidate count/value and an explicit loading/error state. The existing suggestions array is capped at 50, so its length alone is not a whole-library count.

### 3. P2 — Return-visit recap and streak data are disconnected

**Sources:** `components/app-shell/AppDataProvider.tsx:329`, `components/shared/WelcomeBack.tsx:23`, `lib/v2/repositories/dashboard-core.ts:52`.

The V2 bootstrap branch returns before setting `livePlaytime`. That state stays at its zero/empty initial value. The welcome notice still reads the provider's `playtime`, while the V2 Dashboard's actual activity is returned separately as `trend` and never connected to the notice. Its finished-games recap also reads a partial cache rather than complete relevant completion history.

**Reproduction:** with a prior visit on 28 September and a Dashboard response reporting 180 minutes played on 1 October, the “Since your last visit” region was absent at both widths. The provider also never supplies a nonzero streak on a fresh V2 session.

**Recommended correction:** derive the V2 recap from trusted daily gains and a bounded completion query for the relevant visit window. Preserve the existing coverage rules when calculating streaks; unknown observations must not become played days.

### 4. P2 — Progress ordering disagrees with displayed progress

**Sources:** `lib/v2/repositories/library-core.ts:127`, `lib/v2/library-view-model.ts:25`, `app/(product)/library/page.tsx:201`.

The old Library sorted `completionPercent`. The SQL replacement uses manual progress or playtime divided by estimated duration, without the card model's precedence for Completed = 100 and endless = 99. An endless game with little playtime sorts as low progress or unknown even though its card displays 99. Completed games with low playtime can similarly sort below other completed games carrying lower manual progress.

**Reproduction:** a real disposable PostgreSQL fixture sorted descending as displayed percentages **80 → 50 → 99**. The final entry was an endless game with zero observed minutes. This is reproducible in the committed code, independently of the pending fixes.

**Recommended correction:** compute one SQL progress expression matching the card model, including completed/endless/manual/inferred precedence, and use it for the sort key. Add a parity fixture that compares SQL order with the model's displayed values.

### 5. P2 — Added sort ignores valid retained timestamp strings

**Sources:** `lib/v2/repositories/library-core.ts:128`, `lib/v2/repositories/library-product.ts:66`, `app/(product)/library/page.tsx:518`.

V2 retains the original Added string and displays it, but only strings exactly matching `YYYY-MM-DD` produce a SQL sort key. Valid ISO timestamps that the 1.1 `Date.parse` sort recognized become null sort keys and fall back to game ID. This is an edge-case regression; the frequency of timestamp-form Added values in production was not checked. Non-ISO legacy formats need an explicit parsing policy rather than an assumption that they are all safe to parse.

**Reproduction:** retained strings `2026-09-30T12:00:00Z` and `2026-09-01T12:00:00Z` were returned unchanged, but descending Added sorting put the September 1 game before September 30. A game with no Added value also sorted ahead of both because all three keys became null.

**Recommended correction:** preserve raw values while introducing a validated chronological sort projection. Separately decide how newly imported games should receive an Added date: the current owned-publication path does not populate the legacy date table, so the existing control provides no chronology for those new entries.

## Follow-up implementation and verification

Completed 1 October 2026 after the request to fix all findings.

- Wishlist now fetches complete tenant-scoped owned/family AppIDs and edition keys through `/api/v2/wishlist/library-context`. Played/completed taste seeds use the existing diverse selection, capped at 120. Recommendations and ownership badges use this context rather than the partial entity cache. Loading and retry states prevent unchecked purchase recommendations. The shared bootstrap remains bounded.
- Dashboard completion notices consume whole-library candidate count and value, using the same eligibility and dismissal rules as completion review. A 64-candidate fixture verifies that the notice count is independent of the 50-suggestion limit.
- Welcome recaps consume trusted Dashboard daily gains and whole completion counts by day, with only two display titles per day over the bounded visit window. Streaks require consecutive complete observations; missing days and unknown coverage do not become played days. Arrival storage is read once so React Strict Mode cannot overwrite the previous visit during effect replay.
- Progress sorting uses the card model's completed/endless/manual/inferred precedence, including rounded inferred percentages and retained manual decimals. SQL/model parity tests traverse cursor pages in both directions.
- Added sorting validates ISO dates, ISO timestamps with timezone offsets, and legacy British `DD/MM/YYYY` dates. Known dates sort chronologically in UTC; malformed and missing dates sort last in both directions. Original display labels remain intact. This fixes retained-date ordering without inventing acquisition dates for newly imported games whose date is unknown.
- The existing VaultShuffle video loader now covers route transitions and V2 Dashboard, Library, Vault, Collections, completion review and Wishlist loading. The reduced-motion static brand remains available. Browser tests verify actual video playback, static fallback and disappearance after loading.
- The repository CI build fixture now reads the schema's existing project marker instead of attempting an update that violates its fixed marker constraint.

Final verification:

- Main tests: **597 passed**.
- V2 tests: **203 passed**, including isolated PostgreSQL 17, ownership/taste parity, complete completion counts, coverage gaps, date validation and sort pagination.
- Types and lint/theme checks: passed; zero lint errors, 37 existing warnings.
- Production build: passed with an isolated V2 PostgreSQL fixture through a local TLS test proxy. The ordinary local build still selects legacy credentials and cannot query the retired legacy service; no application fallback was introduced.
